# R17.13. Enabling a sandbox after install

R17.13. **Enabling a sandbox after install** warns that the app is **effectively being reinstalled and
its configuration may be reset**: the real files aren't touched, but the app sees an empty private home,
so settings/accounts appear reset, absolute paths stored in its config dangle, and external
integrations (browser native-messaging hosts, MIME associations, autostart) may stop working. AppKata
doesn't import the app's configuration (R17.18). The warning comes before the change: the Sandbox dialog and
Install options say it above Save as soon as a sandboxed choice is picked for an installed app that
runs unsandboxed and has no private home yet. Where Save can't sandbox an installed app that runs
unsandboxed (a launcher in its install folder would find no bubblewrap, R17.4, or the system's
one-time setup is pending or needs a repair, R17.10), they also say there, once a sandboxed choice
is picked, that the choice takes effect once the sandbox can run for the app, and why (what App
Detail says of it); the choice is saved, and AppKata sandboxes the app then, as below. Every way to
set up system support (the install prompt, Settings' Set up…, App Detail's Enable…) first names the
apps it will sandbox and which of them start with fresh settings. When AppKata itself sandboxes an installed app (at start once the
system can, after a setup, or with an update), a notice names it and the Audit records it (review 2,
F13).
