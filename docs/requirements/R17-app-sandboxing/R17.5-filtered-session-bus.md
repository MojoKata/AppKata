# R17.5. Filtered session bus

R17.5. **Filtered session bus.** When the level uses the bus, the launcher starts one `xdg-dbus-proxy`
for the launch (torn down with the app) that exposes the safe part of `org.freedesktop.portal.Desktop`
plus the app's own well-known name (`--own=io.appkata.<app>`, so single-instance and "open in the
running window" work), the portals IBus and Fcitx provide for sandboxed apps
(`org.freedesktop.portal.IBus`, `org.freedesktop.portal.Fcitx`, so the input method works; review 2,
F15, shown in the `inputmethod` harness) and its granted capabilities. An unfiltered bus lets an app reach
`org.freedesktop.systemd1` and start programs outside the sandbox, so filtering is mandatory. The
portals see the app as a host caller (R17.6.1), and some portals trust a host caller with the host, so
the portal name is not opened whole: per-interface `--call` rules allow OpenURI, Settings, Print,
Email and MemoryMonitor (and the Request and Session objects they
create) for every app on the bus, NetworkMonitor and ProxyResolver only with the network grant (they
tell of the host's network, and the second answers with the desktop's proxy settings, which can
carry the proxy's user name and password and which the launcher withholds from an app without the
grant, R17.4; for such an app the launcher sets `GIO_USE_PROXY_RESOLVER=dummy`, since a GLib program
asks that portal before every connection it makes, one to a server of its own on the loopback too,
and a refusal would fail the connection), Notification and Inhibit only with the matching capability
(R17.5.1), `Introspectable` on the portal object (what `gdbus introspect` asks), and nothing else on that
name — not Background (writes the caller's
command into `~/.config/autostart`), DynamicLauncher, Documents, Camera, ScreenCast, RemoteDesktop,
Screenshot, Location, Realtime, Account, Trash, nor FileChooser (R17.6.3), nor the `version`
properties (what Chromium/Electron reads before switching to the portal file chooser; GTK4 is held
by the FileChooser denial itself, R17.6.3). The bus the proxy filters is the session's own: the one
`DBUS_SESSION_BUS_ADDRESS` names, or the runtime folder's (`$XDG_RUNTIME_DIR/bus`) when no address is
set. The launcher shows the proxy that bus wherever it listens: a socket file anywhere on the system
(`dbus-run-session` and `dbus-launch` put theirs under `/tmp` since dbus 1.14), which no working
directory and no folder grant shows the app (R17.3.1), or an abstract socket (R17.9), its `path=` or
`abstract=` read in any place among the address's keys (`guid=` first as well as last), as libdbus and
GIO read it, and a key's name read as GIO reads it, each escaped byte unescaped and the name matched
exactly (`pa%74h=` is its `path=`, which libdbus and sd-bus refuse, and `PA%54H=` no key it knows).
An address that names neither (a list of addresses, a path with an escaped byte, two paths, of which
the proxy's GDBus takes the last, a path with an abstract socket, which no client connects to, a key
with no `=` or nothing before it, as a trailing or doubled comma, a bare `guid` or a comma inside a
path leaves, or a value of any key with an escape that isn't two hex digits or is `%00`, for either of
which the proxy's GDBus refuses the address, another transport) can't be filtered: the launcher says so on stderr, starts no proxy, and the app runs with
no session bus. The proxy is the `xdg-dbus-proxy` the launcher's own `PATH` finds, run from its folder
(`/usr/bin:/bin` where that `PATH` has none), and only one under `/usr` once every link is followed,
the one tree the proxy's own sandbox holds (R17.17). AppKata's own check keeps the same rule
(`bus_filter()` in `src/appkata_core/sandbox.py`): where its `PATH` finds one elsewhere first, it
counts none, so a Standard app runs with no session bus, as where none is installed (R17.1), and App
Detail and Settings → Sandbox name the file found and say to have the `PATH` find `/usr/bin`'s first.
Where the launcher's `PATH` finds one elsewhere all the same, the launcher says so on stderr and the
app doesn't start.

R17.5.1. **Capabilities.** The fiddly desktop-services an app may use, bundled into templates and
mapped to proxy arguments: **notifications** and **screensaver inhibit** (each opens both roads — the
portal interface, which GLib and GTK apps take when they see `/.flatpak-info`, and the direct
`org.freedesktop.Notifications` / `org.freedesktop.ScreenSaver` name the others use — so the
capability is the one switch and an app without it has neither), **tray** (`StatusNotifierWatcher` +
its item name), **media keys** (MPRIS), and **secrets** (`org.freedesktop.secrets`: the Secret
Service on it to consume, or the name owned to provide, e.g. KeePassXC). The direct names of notifications, screensaver inhibit and tray
are opened as the portal's name is, never whole: a name opened whole reaches everything the
connection that owns it serves, and the owner of `org.freedesktop.Notifications` can be the desktop's
own shell (Cinnamon's, on Mint 22.3, where the shell runs what it is sent). So per-interface `--call`
and `--broadcast` rules allow each service's own interface on its own object
(`org.freedesktop.Notifications`; `org.freedesktop.ScreenSaver` on both of its objects, its
`Inhibit` and `UnInhibit` alone and none of its signals, since the same interface also locks the
screen, switches the screen saver on and tells how long the user has been idle, and KDE's screen
locker serves all of it; `org.kde.StatusNotifierWatcher` with the property reads a tray library
makes before it registers its icon), `Introspectable` on those objects, and nothing else of what the
name's owner serves: no other call and, where the filter has upstream's fix for broadcasts (0.1.5,
0.1.8 and later, Debian's 0.1.6 since its security update; R17.17 says what the others let through),
no other signal, on any version of the filter without a known flaw in its filtering (R17.17 names
the two that let an app past it). The secrets name is opened the same way, for the Secret Service alone: its five
`org.freedesktop.Secret` interfaces on `/org/freedesktop/secrets` and the objects below it (the
collections, items, sessions and prompts), with the property calls, listing and signals its clients
use, and not the keyring's own interfaces, which gnome-keyring's connection serves beside it (its
daemon's, which tells the session's SSH agent socket, its master-password one, and the Secret
portal's backend). Password service owns the name only where no other program holds it, nor can the
session bus start one for it, when the app starts: to the filter a name an app may own is one it may
call, so beside the keyring (gnome-keyring holds the name on most desktops, and where it is installed
and not running the bus starts it for the first call to the name, the app's own included) the app
would reach the keyring's whole connection, every unlocked password included. Where another program
holds it or the bus can start one, the launcher starts the app without Password service and says why
on stderr, and so it does where the bus can't be asked (no `gdbus` or `busctl` here, an ask that
fails, an answer it can't read, or none within five seconds); a password manager that is the only
provider keeps it. Media
keys lets the app own its own MPRIS name, the one a review gives it (`Sandbox MPRIS name`, R10.3.1:
a name below `org.mpris.MediaPlayer2`, or with a `.*` suffix that name and every name below it, for
an app that takes a name per instance), and no other: the desktop's media keys reach the app, and
the app reaches no other player but one that holds that same name, since to the filter a name an app
may own is one it may call, whoever holds it (another copy of the same player, the host's own). An
app no review has named may own every name below `org.mpris.MediaPlayer2`, so such an app
can call every other media player on the bus (R17.17); the dialog's hint says which of the two an
app has. No summary chip shows the name, yet a review that names, changes or drops it raises the
review badge and is offered in the dialog ("Use theirs", R17.11), as any other change of what the
app runs with does. The full mapping table is A1.2.3.14, which is also where each capability's names meet:
its word in a review's `Sandbox services` line (R10.3.1), and what this item, the template table
(R17.3) and the Sandbox dialog call it.
