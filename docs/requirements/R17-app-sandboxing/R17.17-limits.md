# R17.17. Limits

R17.17. **Limits**, stated plainly in the UI and docs: on X11 and on every Wayland compositor but GNOME's
the sandbox protects files, not the screen/clipboard/keystrokes (on KDE the clipboard alone, R17.9); a granted folder or network is the app's, the network
reaching every abstract-namespace socket on the host (a session bus among them where dbus is 1.12,
R17.9), and a read-write folder is also a road to the host's programs: a file the app writes there and
opens through the portal is opened by the host's handler for its type, without a question when
that handler is the only one (R17.6.3; Flatpak has the same property); a kernel
exploit leaves any namespace sandbox (this is not a VM); every app, Strict included, can read the
machine's identifiers — the machine-id, the boot id and the host name, and through `/sys` the network
cards' MAC addresses, USB serial numbers and the hardware model — as in Flatpak, and a networked app
can report them (review 2, F18; review 3, R3-7); screen readers can't see a sandboxed app, which
is not given the accessibility (AT-SPI) bus until a filtered proxy for it is built (R17.18; review 2,
F15); running the `.AppImage` or program directly
(or via AppImageLauncher) bypasses the sandbox; there is no per-host/domain network filtering (only
on/off, and per-port via Landlock later); the only seccomp filter is the terminal-injection one
(R17.4); on Ubuntu 25.04 and later, apps that bring their own sandbox (Chromium, Electron) run without
it, inside AppKata's (R17.10.2); and two sandboxed apps with the **tray** capability running at once can collide on the tray
item's bus name — every sandboxed app is one of processes 2 to 6 in its own namespace, so each proxy
owns the same `org.kde.StatusNotifierItem-<pid>-<n>` names, and the second app's icon may not appear (the same
limitation as Flatpak's), and since to the bus filter a name an app may own is one it may call,
either of the two can call the other's connection while that one holds such a name; for the same
reason an app with the **media keys** capability that no review has named (R17.5.1) can call every
other media player on the session bus, and whatever else that player's connection serves, and one
named with a `.*` suffix every app that holds that name or one below it. No network is not no way
out: a Standard app without the network grant can still ask the desktop to open a link or to start
an email (the OpenURI and Email portals, which every app on the bus may call, R17.5), and the link,
which the host opens in the user's browser, may carry what the app knows (R17.6.3; as in Flatpak);
the Sandbox dialog's Network hint says so. The bus filter
(R17.5) is itself a program that reads every message the app sends it, and a fault in it would give
the app what the filter's own sandbox holds: the session bus unfiltered, which is a road to programs
outside the sandbox, and the folder of the filters' sockets, so the filtered buses of the other
sandboxed apps that are running. Beside those it holds only `/usr` and `/etc` read-only, as the app's
own sandbox does: none of the rest of the runtime folder (the ssh and gpg agents' sockets, the
document portal's mount), no network unless the session bus is an abstract socket (R17.9), and none
of the environment AppKata or the app was started with (a terminal's can hold tokens and keys; the
filter gets `PATH`, beside bwrap's own `PWD`), and it runs under the terminal-injection seccomp filter (R17.4).
