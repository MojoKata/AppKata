# R17.14. Uninstalling

R17.14. **Uninstalling** a sandboxed app offers to remove its private home
(`~/.local/share/appkata/sandboxes/<app>`), like any app data (R4.7); so does uninstalling an app
switched Off that still has one (review 2's nit: its home stayed behind, orphaned). A kept home remains that app's
alone (R17.6). A private home is its app's to write, and can hold folders their owner may not open
or change (a module cache kept read-only, a folder at mode 000), so before removing it AppKata gives
each of its folders back to the owner — the folder itself, never what a link in the home leads to —
and then removes the home whole. Where something in it still can't be removed, the uninstall's
notice names the home among what was not removed (R4.7), and what is left stays that app's as a kept
home does: its owner record stays, the same app installed again finds it, and no other app is given
it (CR1.5-20: what couldn't be removed was left without a word, and the owner record removed, so the
data was no app's). What the app was handed through the document portal (R17.6.2) is taken back when
it is uninstalled, and when it leaves Standard for Strict or Off: the portal keeps a file or folder
handed over, under the app's id, for the login session, and an id an uninstall frees goes to the
next app of that name (R17.6), which found them in its own view, to read and to write (CR1.5-25).
An update of a Standard app keeps what the app was handed, since it is the same app under the same
id: only an uninstall, leaving Standard, and a first launcher under an id take it back (CR1.5-56).
AppKata asks the session's document portal, from the host side, to revoke each one for that id: only
for an app its file-argument helper handed something, and without starting a portal where none runs;
where the portal can't be asked the uninstall goes on, AppKata's log says so, and it asks again
before an app is next given a launcher under that id.
