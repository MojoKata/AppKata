# R17.3. Templates

R17.3. **Templates.** A sandbox is normally picked as a named **template** — a preset of level + grants
+ capabilities + Landlock extras — thin and overridable, not a straitjacket. Eight are built in:

| Template | Level | Files | Network | Sound | Devices | Services (R17.5.1) | Landlock (R17.18) |
|---|---|---|---|---|---|---|---|
| `strict` | Strict | none | no | no | X11 only | — | execute-deny |
| `standard` | Standard | none | yes | — | X11 | notifications | execute-deny |
| `offline-editor` | Standard | a folder you pick (rw): Documents or Pictures in one click | no | no | X11 | — | execute-deny |
| `online-app` | Standard | none | yes | play | X11 | notifications | execute-deny |
| `messenger` | Standard | none | yes | play + record | camera, X11 | tray, notifications, inhibit | execute-deny |
| `media-player` | Standard | a media folder you pick (read-only): Music or Videos in one click | optional | play | X11 | MPRIS, inhibit | execute-deny |
| `developer` | Standard | a projects folder you pick (rw) | yes | — | X11 | — | execute allowed |
| `cli-tool` | Standard | the directory it's run in (rw) | optional | — | X11 | — | execute allowed |

The three made for a folder come with none, since which one is the user's to say: picking one offers
it in place ("Pick its folder:", one click for the user folders that fit, **Other…** for any, read-only
under `media-player`), and the summary says "No folder yet" until it has one (review 2, F10: the
table promised a folder and nothing asked for it).

R17.3.1. **Overrides.** Explicit settings override a template; `Sandbox folders: +~/Zettlr` adds to the
template's set (`+`/`-` prefixes add/remove). A template is resolved to a **grant set** before it is
combined or enforced, so it is never an opaque name. Some folders are **never shared**, whoever asks
(a review or the Customize picker): the home folder and anything above it, AppKata's install root
(the folder the app is installed in, and the default one whatever Settings name, since apps
installed there stay there, R4.3.1), its command links folder (R4.3.1.3, on `PATH`: the one
Settings name, the default `~/bin`, and any folder a command link AppKata made is still in)
and data folder (the database, the private homes), the places that make a program start again later
or change what the user's own commands do — `~/.config/autostart`, `~/.config/autostart-scripts`,
`~/.config/systemd` and `~/.local/share/systemd` (user units), `~/.local/share/applications`,
`~/.local/share/dbus-1` (service activation), `~/.local/share/flatpak`, `~/.local/bin` (on `PATH`),
`~/.config/environment.d` and `~/.pam_environment`, `~/.config/plasma-workspace` (KDE's login
scripts), the desktop's own extension and script folders (`~/.local/share/gnome-shell/extensions`,
`~/.local/share/kwin/scripts`, `~/.local/share/plasma/plasmoids`, `~/.local/share/nautilus/scripts`,
`~/.local/share/kservices5`, `~/.local/share/kio/servicemenus` — code there runs inside the shell at
the next login or as the user from a file manager's menu; Mint's Nemo has `~/.local/share/nemo/scripts`
and `actions`, and Cinnamon, Mint's desktop, reads its applets, desklets, extensions and search
providers and the panel's own launchers from `~/.local/share/cinnamon`, and launchers from
`~/.cinnamon` too), the browsers' native-messaging manifests (`~/.mozilla/native-messaging-hosts`, and
`NativeMessagingHosts` under the Chromium family's profile folders in `~/.config` — chromium,
google-chrome, Brave, Edge, Vivaldi, Opera — named one by one, since the match is on exact roots, so
those profile folders are refused too, as folders above one: programs the browser starts on an
extension's request), `~/.local/lib` (Python's user site, where a
`.pth` file runs in every Python the user starts), `~/.local/share/bash-completion` (a command's
completion script, which the shell loads at a tab), a compositor's or window manager's own
configuration, which starts programs (`~/.config/sway` and `~/.sway`, `~/.config/i3` and `~/.i3`,
`~/.config/hypr`, `~/.config/labwc`, `~/.config/openbox`, `~/.config/river`, `~/.config/niri`,
`~/.config/wayfire.ini`), `~/.config/pipewire` (its configuration names programs to start), an
editor's extensions (`~/.vscode/extensions`, `~/.vscode-oss/extensions`), the folders Cargo and Go
put on `PATH` (`~/.cargo/bin`, `~/go/bin`), `~/.gitconfig` and `~/.config/git` (hooks,
aliases), and the shell and session startup files (`~/.bashrc`, `~/.profile`, `~/.zshrc`,
`~/.config/fish`, `~/.xsessionrc`, `~/.xprofile` and their kin, what the default `.bashrc` sources
in turn: `~/.bash_aliases` on Ubuntu and Mint, `~/.bashrc.d` on Fedora, and bash-completion's
`~/.bash_completion` and `~/.config/bash_completion`, and `~/.xinputrc`, which im-config reads as
the session starts; a "folder" grant binds a file
as readily as a folder) — the user's keys (`~/.ssh`,
`~/.gnupg`), the session's runtime folder, and anything inside or above one of these; and the
session bus's own socket file, wherever its address puts it (each one a list names, every `path=` of
an entry, the key's own name read as GIO reads it, unescaped (`pa%74h=`), each judged once its escaped
bytes are read, up to an escaped NUL), and anything above it (a folder beside the
file is not refused for it; `dbus-run-session` and `dbus-launch` put it under `/tmp`, which no
grant shares anyway, below); and every folder, where the address names a socket file AppKata can't read (a path that
isn't absolute, a broken escape, a newline), since the file could be in any. The **system's own
places** are never shared either, whoever asks, nor anything inside or above one: `/proc`, `/sys`,
`/dev`, `/run` (but what is mounted under `/run/media`), `/var/run`, `/tmp`, `/var/tmp`, `/etc`,
`/usr` and `/boot` — a grant is mounted after the sandbox's own `/proc`, `/dev` and `/tmp` and would
put the host's back over them (the host's `/proc` leads to every file of the user's), `/run` holds
the system bus and the container and VM managers' sockets, and `/tmp` other programs' (an ssh
agent's, tmux's) — each judged by the path as it is written, which is where the grant is mounted, and
by where it leads (`/proc/self/cwd` is in `/proc`, wherever it leads); a folder of the home is
judged as the home's, wherever the home is (the list is `SYSTEM_PLACES` in
`src/appkata_core/sandbox.py`). Such a grant
is dropped — the launcher records why, the summary shows it as refused, and the picker says so —
because sharing it would hand the app the real home over its private one, a way to start again
later, the keys the sandbox exists to protect, the unfiltered bus (R17.5), or the system's own files
and other programs' sockets. A grant is judged when
the launcher is written, by AppKata's own session's bus; where the session an app is started in has
its bus socket inside a granted folder all the same, or granted itself, the launcher covers that file,
however the grant shows it (a link to the file, or to a folder above it, followed as the app starts)
and however that session's address names it (a list, every `path=` of an entry, its name escaped too,
an escaped byte, a path up to an escaped NUL, or a link: its target); where that address names a
socket file the launcher can't read,
which could be in any of them, it shows the app each granted folder empty and read-only, covers a
granted socket file, and says why on stderr, and a file named in one of them is handed over through
the document portal (R17.6.2). The list is
`_protected_roots()` and `bus_files()` in `src/appkata_core/sandbox.py`. It is a list of the
places AppKata knows, kept by hand, and it is not complete: a desktop or a program it has not
heard of can load code from a folder of the home that no line of it names, and a grant of that
folder is not refused (R17.17). A grant is refused the
same way when a link on the way to its folder lies in another folder the same app is granted,
whoever made the link and wherever it leads ("a link in ~/Projects, which the app can change, is
on the way to it"): a link there is the app's to make, and the next time AppKata wrote the launcher
it would take what the link names for the folder's place (R17.4; the folder the link names can be
granted itself, and a grant through a link that lies in no granted folder stands). A folder is named from `/` or `~` (`/media/usb`, `~/Projects`); any
other path — a bare word such as `home`, `run/user/1000`, `./x`, an unknown `~user` — is refused the
same way ("not a full path"), since bwrap resolves a bind source from the host's root while the
check would resolve it from AppKata's own working directory (review 2, F1: `Sandbox folders: home`
bound the real `/home`). A path with a `..` in it is refused the same way too, whoever asks ("not a
full path (it has a .. in it: name the folder it leads to)"), unless where it leads is never shared
anyway, which is then the reason said: a grant is shown as it is written, and a review's
`~/Documents/../.cache` read as a folder of Documents (CR1.5-16), and its text without the `..` is
another folder than the one mounted where a step before it is a link. So is a path with a control
character in it — a NUL, a line break, an escape — which no folder a person names has ("not a full
path (it has a control character in it, shown as �)"): it is kept and shown with `�` where each such
character was, the folders beside it on a review's line stand, and no check fails on it (CR1.5-26:
a NUL in one line of a review broke the install card and the install of every app the review
covered). A grant is kept, shown (the
summary, the Audit, the review badge, the launcher) and mounted under one name, whichever way it
was written: from `~` where the folder is in the home and from `/` elsewhere, with no doubled
slash, no `.` step and no slash at its end, so a folder written two ways is one grant (read-only
where one of the two is), and a `-` entry removes it by either.
**Secrets** are refused when a review asks and allowed, with a warning in the summary ("holds
passwords or tokens"), when the user picks them: browsers' and mail clients' profiles
(`~/.mozilla/firefox`, `~/.thunderbird`), other sandboxes' data (`~/.var/app` for Flatpak, `~/snap`),
credentials for clouds, forges and registries (`~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`,
`~/.docker`, `~/.config/gh`, `~/.git-credentials`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, Cargo's,
`~/.config/rclone`, `~/.vault-token`), and password stores (`~/.password-store`, the keyrings, KDE's
wallet), with anything inside or above them. A review's request shows as refused ("a review can't
grant …"). The list is `_secret_roots()` in `src/appkata_core/sandbox.py`. The keyring capabilities
(saved passwords, the password service, R17.5.1) are in the secrets class too: a review asking for
one is refused the same way (review 2, F9).

R17.3.2. **Resolving several sources.** When reviews and the user both weigh in (validated,
`scripts/sandbox/merge.py`):
1. Each review → a grant set (its template, then its overrides).
2. Across Trusts → the least-privilege combination: strictest level; a folder only if **all** grant it
   (read-write only if all do); network, sound, devices and capabilities = the **intersection**;
   of two MPRIS names (R17.5.1) the narrower, a name over none, and no media keys where two reviews
   name different players; execute-deny if **any** Trust denies. One careless reviewer can't widen
   an app.
3. The **user's own choice wins** over the merged reviews; an app **no** Trust has reviewed falls to
   the default template (R17.3.3).
4. A review's `off` adds no limit when merged with others (`off` ∩ X is X), and where the merged
   reviews say Off, the sandbox is **not** turned off: the reviewed baseline of R17.3.3 applies, and the
   install card and the Sandbox dialog offer "X suggests no sandbox — Use theirs", which makes Off the
   user's own choice (review 2, F8).

R17.3.3. **Defaults, by app kind and review state.** Reviewed beats unreviewed. A reviewed GUI app uses
the review's template (baseline `standard`); a reviewed CLI tool uses the review's template (baseline
`cli-tool`); an **unreviewed GUI app** uses `strict`; an **unreviewed CLI tool** uses `cli-tool`
(real protection, not Off). Every default is one click to change in the install options (R4.9) or App
Detail. **The app's kind** is decided from the download, once its files are placed and before its
launcher and menu entry are written (review 2, F4): an AppImage is a command-line tool when the
`.desktop` at its root says `Terminal=true` (its own runtime reads it out, in the unpacking's
sandbox, R17.7); a tarball is one when its `.desktop` files say so, or, with none, when its program
links no display library (X11, xcb, Wayland, GTK/GDK, Qt's GUI, SDL, OpenGL/EGL, Vulkan; Electron links
GTK) and no shared library beside it, in its folder, links one (Firefox's program links none and
loads its `libxul.so`, which does, at run time). What can't be told (a script, no bwrap) counts as an app — Strict, the tighter. The user's own
choice in the install options ("It is: an app with a window / a command-line tool", R4.9.2) wins, and
correcting it on an installed app with no sandbox of the user's own applies the default for the new
kind at once. A command-line tool gets no app-menu entry when that option was only Settings' default
(R4.3.1.1). The `cli-tool` template binds the directory the tool is run in (rw) via the command-link
wrapper (R4.3.1.3) and nothing else of the home; a path outside that directory isn't visible, so a tool
that needs wider paths can take a folder grant or Off. The directory is **not** shared when it is the
home folder, a folder above it (including `/`), one of the never-shared folders of R17.3.1, or
inside or above one of those, or above the
session bus's socket file wherever the session's address puts it (read before the directory is
judged, every form `bus_files()` reads and a link's target too: `/tmp` in a `dbus-run-session`
session; and where the address names a file the launcher can't read, a path that isn't absolute, a
broken escape or a newline, no directory is shared) — that would be the whole home or more, a way to
start again later, or the real session bus, not a project folder; the tool then runs in its private
home and says why on stderr. A **system place** of R17.3.1 is one of those never-shared folders: run
from `/tmp`, `/var/tmp` or `/dev/shm`, from a folder in one, or from `/var`, which is above two, the
tool is not given the directory, which would be mounted over the sandbox's own with other programs'
sockets and shared memory in it, and its line on stderr names the system's folders; what R17.3.1
leaves to a grant is left to the tool too, a folder of the home wherever the home is, and where a
stick or a disk is mounted (`/media`, `/mnt`, `/run/media`); a file named on the command line is
handed over all the same, one under `/tmp` too (R17.6.2).

R17.3.4. **Personal templates** (naming the user's own paths) and **reviewer-defined** templates
aren't built (R17.18); there are the eight built-in templates plus per-app customization: a template the user
changes is kept as that template plus the changes, shown as "Offline editor · customized" with **Reset
to template**; only a merged or bespoke set is "Custom" (review 2, F10). The Sandbox dialog describes
such a set by its changes ("Standard, without the network and notifications, with ~/Projects
(read-write)"), not with the template's own description (review 2's widened-Strict nit).

R17.3.5. **What a review may do.** Reviews are suggestions from people the user trusts, who may be
wrong or compromised. On its own a review may pick a template, narrow access and grant ordinary
folders, sound, devices, services and the writable app folder (R10.3.1); it may not turn the sandbox
off (R17.3.2) nor grant the user's secrets (R17.3.1) — those take the user's own click. The never-shared folders (R17.3.1) are refused whoever asks (review 2, F8).
