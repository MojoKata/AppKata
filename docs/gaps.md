# AppKata — Gaps and proposals

Gap analysis of [`requirements.md`](requirements.md), drawing on the Obtainium project
(<https://github.com/ImranR98/Obtainium>).
Section references (e.g. "5.6") point into `requirements.md`. Decisions still needed are
listed at the end.

---

## 1. Toolkit and style (req 1)

- **Code:** Python (the version the release carries, req 1.2), PySide6 (Qt 6 with QML), with the `Basic` Qt Quick Controls style.
- **Window:** it draws its own header bar. The header holds the app icon and name, a segmented
  view switcher (**Apps · Catalog · Sources**), an app menu (⋮) and a close button.
- **Look:** the `Theme.qml` design tokens (bg `#15171e`, surface `#1f222b`, accent
  `#8089ff`, and their light-theme counterparts), with dark as the main design target. Soft
  cards, generous spacing, and closable detail panels docked on the right.
- **Tiles:** responsive tiles that scale with their width, keeping their aspect ratio.
- **Feedback:** errors appear as short-lived toasts. Markdown is rendered by Qt (`Text.MarkdownText`).
- **Mockups:** generated by `screenshots/src/render.js`: SVG rendered to PNG with
  `@resvg/resvg-js`, using Cantarell and DejaVu Sans Mono, in both `mocks/dark` and `mocks/light`.
- **Gap:** a macOS `.app` bundle, code signing and notarization are new work.

## 2. From a project URL to its releases (req 2.1)

### Reliable

| Host | Releases API | Notes |
|---|---|---|
| GitHub | `api.github.com/repos/{o}/{r}/releases` | Rate limit is 60 requests/hour without a token. Use `/releases/latest` to verify the latest release. |
| GitHub Enterprise | `{host}/api/v3/repos/{o}/{r}/releases` | Same API as GitHub |
| GitLab (gitlab.com and self-hosted) | `/api/v4/projects/{urlencoded path}/releases` | Subgroups. Assets may be in `assets.links` or in `/uploads/…` links in the release description. |
| Gitea, Forgejo, Codeberg | `/api/v1/repos/{o}/{r}/releases` | Gitea and Forgejo are identical here |

### Unreliable, or no releases concept

| Host | Problem |
|---|---|
| SourceHut | No release object. Files are attached to refs. Obtainium reads `{repo}/refs/rss.xml` and scrapes each ref page. |
| Bitbucket | "Downloads" area, not tied to tags or versions |
| Gogs | Releases in its web pages but no releases API |
| Launchpad | Different model: series, milestones and files |
| Pagure | Release tarballs are optional uploads |
| Azure DevOps | No releases; uses artifact feeds |
| AWS CodeCommit | No releases, and the service is being wound down |
| Radicle | No releases |
| cgit, gitweb, plain git over HTTP | Tags only, no binaries |
| ngit / Nostr (NIP-34) | Repo announcements (kind 30617), state and patches, but no release events. Zapstore publishes app, release and NIP-94 file-metadata events, which is worth evaluating. |

### Custom domains

Obtainium only matches hard-coded hosts. On any other domain, the user has to choose an
"Override source" by hand. **Proposal:** AppKata detects the forge automatically:

1. Probe `/api/v1/version` (Gitea/Forgejo).
2. Probe `/api/v4/version` (GitLab).
3. Probe `/api/v3/meta` (GitHub Enterprise).
4. Read the HTML `<meta name="generator">` tag.
5. If none of these identify the forge, offer a manual override.

### ngit

1. Resolve the `nostr://` or `naddr` reference to its repo announcement.
2. Read its `clone`/`web` URLs and its `maintainers`.
3. If a web URL is on a known forge, use that forge's releases.
4. Otherwise, fall back to tags plus track-only, unless the repo publishes release events or
   an AppKata manifest (see §5).

## 3. Direct releases link and per-source overrides (req 2.2)

Support a direct releases-page URL. A URL alone isn't always enough, so every Source also gets
optional overrides, taken from Obtainium:

- **Source type override.**
- **Include prereleases.** Draft releases are always skipped.
- **Release-title filter regex** and **version-extraction regex** (with a match group).
- **Asset filter regex** for each OS and architecture, with an invert option. The automatic
  filter is applied only when it narrows the list without emptying it.
- **Fall back to older releases** when the newest release has no matching asset.
- **Use the release date as the version.**
- **Track only:** notify about updates without installing anything.
- **Sort order:** smart name, falling back to date.
- **Count re-uploaded assets as new:** an asset uploaded again to an old tag counts as an
  update.

### Fallbacks

- **Hosts without releases:** tags plus track-only.
- **Generic HTML source:**
  1. Collect links.
  2. Filter them with a regex.
  3. Optionally follow intermediate links, a chain of regexes.
  4. Optionally extract the version from the page.
  5. If no version string is found, use a pseudo-version (ETag, link hash, or a hash of the
     first bytes of the file).

### Errors

Use typed errors that drive the UI and retries: `NoReleases`, `NoMatchingAsset`, `NoVersion`,
`RateLimited`, and `RepositoryRenamed`. The last one offers to update the stored URL.

## 4. Installing and uninstalling (largest gap)

The requirements don't yet say what "install" means on each OS.

### Asset types

| OS | Asset types |
|---|---|
| Linux | AppImage, Flatpak bundle, .deb, .rpm, tarball |
| macOS | .dmg, .pkg, zipped .app |
| Windows | .msi, .exe installers (Inno, NSIS, WiX), portable .zip, .msix |

### Choosing the asset

Match the OS and the architecture (x86_64, arm64, universal), and allow a per-Source regex
override. Use an optional manifest (see §5) when the repo provides one.

### Silent installs

- MSI: `msiexec /qn`
- Inno Setup: `/VERYSILENT`
- NSIS: `/S`
- Unknown installers: run them interactively.

### Elevation

pkexec on Linux, UAC on Windows, an admin prompt on macOS. Ask for it per action. AppKata
needs no background service.

### Portable apps

- Install to `~/.local/share/appkata/apps` or `%LOCALAPPDATA%\Programs\AppKata`.
- Create a `.desktop` entry or Start-menu shortcut.
- On macOS, copy the app to `~/Applications` or `/Applications`.

### Uninstalling

Remove through the package manager, run the Windows registry `UninstallString`, or delete the
bundle or portable folder.

### Already-installed apps

Should the Apps list (6) include only apps AppKata installed, or also adopt apps that are
already installed? If adopted, match them by version from the package database, the registry,
or `Info.plist`. Obtainium compares versions only when both strings look standard, and
otherwise doesn't guess.

### Apps with no binaries

Apps that ship only source code are track-only.

## 5. Icons, hero images and descriptions (5.1)

There's no standard for these. Proposed fallback chain:

1. An optional **`.appkata.toml`** in the app's repo. It declares the icon, hero image, asset
   patterns for each OS and architecture, the install type, and the silent-install flags. This
   also helps with ngit and with hosts that have no releases.
2. AppStream `*.metainfo.xml`: name, summary, icon, screenshots.
3. Fastlane metadata (`fastlane/metadata/android/en-US/images/icon.png`,
   `featureGraphic.png`).
4. The forge's social-preview or Open Graph image (the GitHub GraphQL field
   `openGraphImageUrl`).
5. The first image in the README.
6. The owner's or organization's avatar.
7. A generated gradient tile showing the app's initial.

### README handling

- Resolve relative links and images against the raw-file URL.
- Sanitize any HTML.
- The "first paragraph" (5.2.2) is the first prose paragraph. Badge rows, headings and
  HTML-only blocks are skipped.

## 6. Download verification

The requirements cover signed `AppKata.md` commits but say nothing about the binaries.
Proposed checks:

- `SHA256SUMS` or `*.sha256` files when present.
- minisign, GPG or sigstore/cosign signatures, and GitHub artifact attestations, when present.
- OS code signing: Authenticode on Windows, notarization and Gatekeeper on macOS.
- On macOS, handle the quarantine flag.

Show a **Verified / Checksum only / Unverified** chip in the App Detail panel.

## 7. Signatures and Authorities (7.2.3–7.2.7)

- **Supported signature types:** to decide. Options are GPG, SSH, X.509 (gitsign), and Nostr
  keys for ngit.
- **An Authority is the signing key's fingerprint,** saved on first use when the Trust is added
  (trust on first use). Show the key in a confirmation step.
  - The forge's "Verified" badge is not enough, because that means trusting the forge.
- **Where names and avatars come from:**
  - ngit: the maintainers' npubs, with name, avatar and NIP-05 from their kind-0 profiles.
  - GPG/SSH: the forge account linked to the key, or Gravatar, falling back to an identicon.
  - The hover popup (7.2.5.2) shows the name, email/NIP-05, key type and fingerprint, when the
    key was first and last seen, and its enabled state.
- **Which commits must be signed:** every commit that touches `AppKata.md` since the last
  verified commit. Checking only the latest commit isn't enough.
- **Rewritten history:** a force-push that rewrites history counts as an unsigned change
  (7.2.7.1).
- **Disabled Authorities:** a disabled Authority's later signatures count as unsigned. Its
  earlier signatures stay valid.

## 8. Trust scores (5.5, 5.6)

- **Combining several Trusts:** the requirements don't say how. **Proposal:** if any enabled
  Trust gives 0, the app is hidden unless searched for, with a warning (a veto). Otherwise
  show the average Trust and average Rating, and list each reviewer in the detail panel.
- **Unrated is not 0:** an app with no review at all gets an "Unreviewed" badge and is not
  hidden.
- **Your own AppKata.md** counts as a Trust implicitly. It always applies and has its own
  Authority, your signing key.
- **Installing a Catalog-only app:** an app that appears only in a Trust file is added to
  Sources automatically when it's installed.
- **Bootstrapping:** should the first run offer a starter Trust?

## 9. Sync and updates (5.1.1, 7.1.3, 7.1.4)

- **What Sync refreshes:** Sources (releases, metadata, images), Trusts (fetch and verify), and
  the README cache. Show progress in the header and allow cancelling.
- **Background checks:** a setting for the check interval, plus a notification for new
  updates. Should AppKata keep running in the tray?
- **Concurrency and rate limits:** about 4 fetches at once (Obtainium's default). Use per-host
  API tokens and honour `x-ratelimit-reset` and `Retry-After`. Tokens are scoped to their
  host and never sent to another domain.
- **Offline:** serve everything from the sqlite cache and show the time of the last sync.
- **Cache location:** the per-OS standard directories (`QStandardPaths`).
- **Version comparison:** semver-aware, falling back to release date.
- **Pinned and too-young updates:**
  - Minimum age (7.1.4) is in days. Obtainium calls this `minimumUpdateAgeDays`.
  - In Apps, a pinned update or one younger than the minimum age shows
    **"Pinned"** or **"Held · 3 days left"** instead of an Update button. It does not sort to
    the top.
- **Schema versions:** version the sqlite schema and the manifest from day one. Obtainium
  needed a migration layer later.

## 10. Missing UI pieces

### Catalog

- An **Install** button in the App Detail panel. The requirements only list Update and
  Uninstall.
- An "Installed" or "Update available" mark on tiles.
- A trust/rating star badge on tiles, and tag chips (warning tags in the warning color).
- Tag filter chips and a sort order (trust, rating, recently updated, name) next to the search
  box.
- Show apps with a Trust of 0 in search results, dimmed and with a warning (5.6.1).

### App Detail panel

- Release notes for the latest release.
- A version picker for rolling back.
- Each reviewer's Trust, Rating and section text.
- The verification chip (§6).
- The source URL.

The review pencil (6.4.3) should also appear in the Catalog's detail panel, so you can review
an app you haven't installed.

### Sources

- An **Add Source** dialog: enter a URL, detect the host type, preview the icon, name and
  latest version, and set optional overrides (§3).
- **Remove** asks whether to uninstall (7.1.2.1). If you keep the app, warn that it will get no
  more updates (7.1.2.2).
- Pin and minimum-age controls on each row.
- Row states: error (with the typed error), rate-limited, renamed.

### Trust

- An **Add Trust** dialog: enter a URL, find `AppKata.md` (in the root or `docs/`), verify the
  signature, and show the Authority key to confirm.

### Settings

Reached from ⋮. Holds:

- API tokens per host.
- The path to your AppKata.md.
- The sync interval.
- The install location.
- The default for prereleases.
- The theme (Match system, Dark, Light).

### ⋮ menu

Sync, Settings, Theme, About, Quit.

### Empty states

Shown on first run when there are no Sources or Trusts yet.

### Deep links (from Obtainium)

- An `appkata://add/<url>` handler.
- A "Get it on AppKata" badge that falls back to a web page for visitors without the app.

### Import and export

Sources, Trusts and settings as JSON. A plain list of URLs can also be imported.

## 11. AppKata.md format (8)

- **Finding the table:** the first GFM table whose header row is exactly
  `App | Source | Tags | Trust | Rating` (case-insensitive). A title or introduction may come
  before it.
- **Matching apps:** apps are keyed by their **Source** column, after normalizing the URL:
  1. Strip `.git` and any trailing `/`.
  2. Compare the host case-insensitively.
  3. Map SSH URLs to HTTPS.

  App names must be unique within a file, so that the `# Appname` sections (8.2) are
  unambiguous.
- **Trust and Rating values:**
  - Accept `0`–`5`, `⭐`×n, and `★`/`☆` forms.
  - An **empty cell means no opinion**, which is different from 0.
  - Invalid values are reported as parse warnings on the Trust row.
- **Missing or unknown sections:** a table row with no matching section is valid. A section
  with no matching row is ignored, with a warning.
- **Creating the file:** if your AppKata.md doesn't exist, the review dialog creates it with
  the table header.
- **Editing:** the editor changes only the app's own row and its `# Appname` section, and keeps
  everything else in the file as it is.

### Signing on Save (6.4.3.3.5)

1. Commit.
2. Run `git verify-commit HEAD`.
3. If it fails, don't push. Notify the user and offer **Amend with signing** or **Open signing
   settings**. Check `commit.gpgsign` and `gpg.format` in advance, and warn in the dialog
   before Save.

### Trust/Rating picker (6.4.3.3.1)

- Clicking `-` sets 0 ("avoid"). Clicking a star sets 1–5.
- A separate clear (×) action sets "no opinion".
- Use an icon font for the stars, or draw them as SVG.

## 12. Tags (8.1.2.3)

- **`sass`:** probably meant **SaaS**. Since the definition is "an account is required",
  `account` may be a clearer name. Decide before the format ships.
- **Tags are case-insensitive** (8.1.2.3.2). Store them in lowercase and display them in
  lowercase.
- **Suggested additional tags,** mostly from F-Droid's anti-features list:

| Tag | Meaning |
|---|---|
| `ads` | Shows advertising |
| `tracking` | Telemetry or analytics, including opt-out ones |
| `nonfreenet` | Relies on a non-free network service |
| `nonfreedep` | Depends on non-free libraries or components |
| `nonfreeassets` | Artwork, sound or data under a non-free license |
| `upstreamnonfree` | The upstream source contains non-free parts that are stripped out |
| `knownvuln` | Has a known, unfixed security vulnerability |
| `unmaintained` | No upstream activity for a long time |
| `archived` | The upstream repository is archived or read-only |
| `nsfw` | Adult content |
| `reproducible` | Reproducible builds have been verified |
| `signedbinaries` | Release binaries are signed or have checksums |
| `offline` | Works fully without a network |
| `portable` | Runs without installation |

## 13. Decisions (resolved 2026-10-01)

These answers are now part of [`requirements.md`](requirements.md).

1. **Apps list scope:** AppKata manages only the apps it installed. Apps installed some other
   way are flagged wherever they are listed or added, and AppKata never installs on top of
   them (req 4.5).
2. **Trust combining:** a Trust of 0 from any enabled Trust is a veto. Otherwise the values
   are averaged (req 10.6).
3. **Signature types:** GPG, SSH and Nostr. X.509 is not needed (req 10.7).
4. **Pickers:** in the Trust picker, `–` sets 0 (Avoid, a veto). In the Rating picker, `–`
   is just 0 stars. Both have a separate clear action for "no opinion" (req 8.4.3, 8.4.4).
5. **Tag name:** `saas` (req 10.4.2).
6. **Linux formats:** AppImage, then Flatpak, then .deb/.rpm, then tarballs (req 4.2).
7. **Background running:** a tray icon with a menu that includes **Quit AppKata**. The ⋮ menu
   has **Close window** and **Quit AppKata** (req 1.7, 5.4).
8. **Starter Trust:** none. Trusts are added only by the user, and Sources alone are enough
   (req 10.5.2).

## 14. Second round (resolved 2026-10-01)

These answers are now part of [`requirements.md`](requirements.md).

1. **ngit releases:** use Zapstore's NIP-82 events:
   - Kind 32267, the software application.
   - Kind 30063, the release.
   - Kind 3063, the asset. The legacy kind 1063 (NIP-94 file metadata) is also read.

   Zapstore's relay code also defines kind 30267, the app "stack", a curated list of apps.
   This could later serve as a Nostr-native Trust list (req 2.4.3.1).
2. **Catalog sort default:** Trust, then name (req 12.2).
3. **Background sync:** every 6 hours (req 9.3).
4. **Origins:**
   - An app comes from a Source (one the user trusts themselves), from Trusts (reviewers'
     claims), or from both. Trust apps are never copied into Sources.
   - Each app shows its origins and links to its Trusts, and its detail panel lists each
     Trust's review.
   - A Source that Trusts also list is flagged with those Trusts (req 2.9, 5.7.3, 5.7.6, 7.1.1).

   As a result, pinning and minimum age now belong to the app instead of the Source, so they
   also work for installed apps that come only from a Trust (req 9.5).

## 15. Found while building the Linux slice (2026-10-01)

- **Zipped packages.** Some projects wrap their Linux packages in `.zip` files (Flameshot 14:
  `…-artifact-appimage-x86_64.zip`). AppKata currently says "No download for this computer".
  Looking inside archives, as Obtainium's *include zips* option does, would fix it.
- **Releases without files.** Signal Desktop's GitHub releases have no files (it ships through
  its own apt repository), and Upscayl's newest release is a bare tag. A release with no files
  is now skipped (requirement 9.4); apps like Signal show their version but no download.
- **GitHub's anonymous rate limit is per IP address.** On a shared or NAT'd address it can be
  used up by others; AppKata falls back to github.com's pages (requirement 2.4.1), which also
  carry SHA-256 digests. A token is still the better experience.
- **Old OpenSSH.** RHEL 8 (8.0) and Windows 10's built-in OpenSSH predate `ssh-keygen -Y`, so
  AppKata verifies SSH signatures itself (requirement 10.7). *Signing* your own reviews with
  SSH still needs OpenSSH 8.2+ (git does the signing); GPG works everywhere.
- **Icons.** Repositories hold many images named `*logo*` or `*icon*` (documentation logos, UI
  icons like `alert-icon.svg`). The ranking prefers the shipped app icon (`linux/icons`,
  `hicolor`, `build/icon.png`, AppStream) and names matching the app; and the backend picks a
  light or dark plate behind transparent icons so white or black glyphs stay visible.
- **Network reach where it was developed.** Only GitHub and PyPI were reachable, so GitLab, Codeberg and
  keys.openpgp.org paths are covered by tests with recorded responses, not live calls.

## 16. Third round (resolved 2026-10-01)

These answers are now part of [`requirements.md`](requirements.md) (sections 5.7.5, 7.7, 8.4, 13, 14).

1. **Audit scope:** both what you do and what AppKata does on its own, each labelled **You**
   or **Sync** (req 13.3).
2. **Audit placement:** a fourth segment in the perspective switcher (req 5.1). Its screens
   use the prefix **U**.
3. **Older versions:** installing one pins the app at that version (req 5.7.5.1).
4. **ngit in Explore:** search the relays and open results on gitworkshop.dev; "Add source"
   stays disabled until ngit Sources exist (req 7.7.3).

Defaults chosen without asking:
- **Explore services:** GitHub, GitLab.com and Codeberg.
- **App log folders:** `$XDG_STATE_HOME/appkata` on Linux, `%LOCALAPPDATA%\AppKata\Logs` on
  Windows, `~/Library/Logs/AppKata` on macOS.
- **Audit immutability:** enforced with database triggers.

Not reachable from the development machine: GitLab.com, Codeberg and the Nostr relays. Their searches are
tested with recorded responses and a local fake relay.

## 17. Live GitLab check (2026-10-01)

GitLab.com became reachable from the development machine; invent.kde.org, Codeberg, gitworkshop.dev and the
Nostr relays still aren't (the TLS handshake is cut off). Syncing gitlab.com/inkscape/inkscape
and searching GitLab in Explore worked, and turned up two fixes:

- **AppStream names:** the parser took `<developer><name>` ("The Inkscape Community") instead of
  the component's own `<name>`.
- **Version tags:** tags like `INKSCAPE_1_4` are now read as version 1.4, and names like
  "Inkscape 1.4.2" as 1.4.2.

Inkscape's GitLab releases carry only the source tarball (its AppImage is on inkscape.org), so
AppKata correctly finds no download for Linux there.

## 18. Settings and portable apps (2026-10-02)

The full Settings dialog (req 11.1) replaces the first sketch. Portable-app options:

- **Install folder** for the versioned files, and a separate **command links folder** (default
  `~/.local/bin`) for one short link per app. This keeps `~/bin`-style folders free of app
  folders and version numbers.
- **Stable name** (`LocalSend.AppImage` → the versioned file) and **app menu** entries, both on
  by default. Launchers point at the stable name, so updates don't break them.
- Changing the install folder applies to new installs only.
- Not built yet, worth considering: keeping the previous version's file for a quick rollback,
  and a per-app override of these options.

## 19. Portable or system package (2026-10-02)

Determined from the file (req 4.2.1), not a setting. Only two cases ask, on the first install
(req 4.9): a release with both kinds of file, and a Windows `.exe` that is neither recognizably an
installer (Inno, NSIS, WiX, InstallShield markers) nor named portable/setup. The answer is saved
per app. Windows `.exe` handling is implemented in the core but can only be exercised with the
Windows build; uninstalling apps installed by their own installer waits for it too.

## 20. Fourth round (2026-10-02)

- **Install layout:** `~/bin/apps/<app>/` with versions side by side; command links in `~/bin`.
  Windows `C:\Programs`, macOS `~/Applications` (req 4.3.1). Older versions are kept (default 2)
  and reinstall without downloading (req 4.3.1.5).
- **Per-app options** copied at install; `<App>::AppKata::Settings` sub-sections are written by
  the review dialog and used by followers as recommended starting values (req 4.3.1.6, 8.4.7,
  10.3.1).
- **Minimum age** is global, with per-Source and per-app overrides (req 9.5.2).
- **Locations** of the database and log follow each platform's convention (req 1.8).
- **docs/AppKata.md:** 30 apps chosen from ~50 candidates by downloadable releases and the absence
  of a self-updater on any platform, found by scanning each project's source (paths and update
  code). Trust and Rating come from a published rubric (signatures, checksums, release age,
  stars); they're a starting point to review before signing the file. Generated by
  `scripts/make_appkata_md.py` from `scripts/data/appkata-md-facts.json`.

## 21. Fifth round (2026-10-02)

- **Trust Score** (req 7.6.8): 1–5 stars, no 0. New Trusts start at 3; the user's own file is
  fixed at 5. It weights both Trust and Rating in the combined score (req 10.6.2), so a 5-star
  Trust counts five times a 1-star one; a 0 Trust still vetoes whatever the Score. Trust lists
  and popups sort by Score, then name (req 7.6.7). Scores are exported and imported, and changes
  are audited. Score stars use the accent colour so they don't read as a Rating.
- **Self-update** (req 2.11): AppKata's repository is a built-in Source. The URL was a placeholder
  in `appkata_core/__init__.py` until 2026-10-25, when it became the real one,
  `github.com/MojoKata/AppKata`. As an AppImage it adopts its own file on first start, updates like any portable app,
  then offers **Restart AppKata**. Run from source or a package it only notifies and opens the
  releases page. It can't be uninstalled, and its Source can't be removed.
- **Minimum age** is now global only (req 9.5.2): the per-app and per-Source overrides are gone
  (the `app_settings.min_age` column stays, unused, so older exports still import).
- **About dialog** (req 5.4.1) has the license, project link, platforms and **Check for updates**.
- Settings **Browse** buttons are icon-only folder buttons.

## 22. Sixth round (2026-10-02)

- Install dialog: "Options recommended by <Trust>", without "in their AppKata.md".
- Settings: switches lost the Basic style's padding, so every control ends on one right edge
  (req 11.1).
- AppKata's description is "A FOSS app store built on git. Apps come from your Sources and from
  Trusts." (About dialog and the demo's AppKata README).

## 23. Seventh round (2026-10-02)

- **Install progress** (req 4.8): phases Waiting / Downloading / Verifying / Installing; one install
  at a time, the rest queued; percentage, size and speed on the row and in the App Detail panel;
  "Installing 45%" on tiles; a turning icon in the header. Cancel until Installing starts.
- **Resumable downloads** (req 4.8.2): `.part` files with `Range` + `If-Range`, three automatic
  retries, and resuming on the next Update after a failure or quit. Weak ETags don't resume.
- **Confirmations** (req 5.8) for every removal, Trust signer / Ignore, and Quit during an install,
  in the existing style (Cancel plus an action-named, red button). Remove trust now lists
  installed apps with no other origin and offers **Keep updating as my sources** (req 7.5).
- **`signed`** replaces `signedbinaries`; old files aren't read for it.
- **Auto update** (req 4.10, 10.3.1): `yes`, `no`, or platforms; the highest-Score Trust's value
  applies unless you set it per app. Self-updating apps are tracked, not updated; portable ones

## 30. Windows (2026-10-03)

Until now Windows was covered only in passing: a row in most tables, and Windows code in the core
that has never run on Windows. This section lists what the requirements leave unsaid for Windows,
what the code is missing, and the decisions needed before the Windows release.

### Already in place

- Paths: data in `%LOCALAPPDATA%\AppKata`, the log in `…\AppKata\Logs` (req 1.8, 14.3), portable apps in
  `C:\Programs` (req 4.3.1).
- Choosing an asset: the format order `.msi`, `.exe`, `.msix`, `.zip` (req 4.2), and classifying a `.exe` by
  reading its first megabyte (req 4.2.1, mockup C09).
- Installing: silent arguments for MSI, Inno, NSIS, WiX and InstallShield (req 4.3.3), a portable `.exe` or
  `.zip`, and success on exit code 0 or 3010.
- Opening folders (`os.startfile`) and the log in Notepad (req 14.5.2). The tray and its notifications use Qt's
  `QSystemTrayIcon`, which also works on Windows.

### Gaps in the requirements

1. **Elevation (req 1.3).** The requirements say "UAC", but not how. A per-machine `.msi` run with `/qn` has
   no UI to show a UAC prompt, so it fails instead of asking (1603/1625). An installer whose manifest requires
   administrator rights can't be started with `CreateProcess` (error 740). Both need `ShellExecuteEx` with the
   `runas` verb, and the exit code then has to be read back from the process handle.
2. **Per-user or per-machine installers.** Many installers can install for the current user only, which needs
   no UAC prompt: electron-builder's NSIS (`/currentuser`), Inno Setup when the installer allows it
   (`/CURRENTUSER`), and MSI (`ALLUSERS=2 MSIINSTALLPERUSER=1`). The requirements don't say which AppKata
   prefers. Per-user would match the portable install folder, which also needs no administrator rights.
3. **Installers that aren't listed.** Squirrel.Windows (`--silent`; installs per user into `%LOCALAPPDATA%`
   and updates itself, which is common for Electron apps), WiX Burn bundles (`/quiet`) and Advanced Installer.
   Exit codes other than 0 and 3010 aren't covered: 1641 (a restart was started), 1602 (cancelled by the
   user), 1618 (another install is running). Nothing tells the user when a restart is needed.
4. **Uninstalling installer apps (req 4.9.6).** AppKata should do this itself instead of sending the user to
   Windows Settings:
   1. Snapshot the Uninstall registry keys (HKLM 64-bit and 32-bit views, and HKCU) before and after the
      install, and record the new or changed entry: its `DisplayName`, `DisplayVersion`,
      `QuietUninstallString` or `UninstallString`, and for MSI the product code (`msiexec /x {code} /qn`).
   2. Uninstall with `QuietUninstallString`, or with `UninstallString` plus the silent argument for its
      installer type, elevated when the entry is under HKLM.
   3. After an update, read `DisplayVersion` again to confirm the installed version.
5. **`.msix` (req 4.2.1, 4.3.3).** It's listed as a system package that needs elevation. In fact
   `Add-AppxPackage` installs it per user with no UAC prompt, but only when the package's signer is trusted;
   a self-signed `.msix` fails. AppKata uninstalls it with `Remove-AppxPackage` and the package's full name.
   Nothing for `.msix` is built yet.
6. **The portable install folder (req 4.3.1).** The default `C:\Programs` can be written by every user of the
   computer. By default, Windows gives Authenticated Users Modify rights on everything created under the root
   of the system drive. Another account could replace a program that you then run. Options:
   - `%LOCALAPPDATA%\Programs`. This is Windows' own per-user location, also used by VS Code's user installer
     and by Squirrel. It was the first proposal (§4).
   - Keep `C:\Programs`, and remove inherited permissions from each app's folder so only its owner can
     change it.
7. **Start-menu shortcuts (req 4.3.1.1).** The requirements don't say where shortcuts go or what they hold.
   Proposal: a `.lnk` in `%APPDATA%\Microsoft\Windows\Start Menu\Programs\` (one level only; Windows 11's
   Start menu shows only one folder level), using the program's own icon, its folder as the working directory,
   and an AppUserModelID so the app pins and groups correctly on the taskbar. Shortcuts are rewritten on each
   update (req 4.3.1.2).
8. **Command links (req 4.3.1.3).** Symbolic links need Developer Mode or administrator rights, and `~/bin`
   isn't on the PATH on Windows. Proposal: a `<app>.cmd` shim (or a small `.exe` launcher, as Scoop uses, so
   Ctrl+C and exit codes behave) in `%LOCALAPPDATA%\AppKata\bin`. That folder is added to the user's PATH
   (`HKCU\Environment`, then broadcast `WM_SETTINGCHANGE`) when the first shim is made, and removed from the
   PATH when the last one goes.
9. **Files in use.** On Windows a running program's `.exe` and DLLs can't be deleted or replaced. Updating,
   switching versions, removing a kept version or uninstalling a running portable app fails partway through.
   Proposal: before the Installing phase, check whether any process runs from the app's folder. If one does,
   ask "Close <App> to continue" with **Retry** and **Cancel**, and never stop the app without asking.
   Installers usually handle this with the Restart Manager, so this applies only to portable apps.
10. **AppKata updating itself (req 2.11).** The requirements cover only the AppImage. Under 2.11.4 the
    Windows build, which is installed with Inno Setup, would only *notify*. Proposal: download the new
    `AppKata-<version>-setup.exe`, verify it, show **Restart AppKata**, and then run it with
    `/VERYSILENT /SUPPRESSMSGBOXES` plus a flag that relaunches AppKata. Inno's `CloseApplications` stops the
    running copy.
11. **Starting at login (req 1.7.4).** The autostart mechanism isn't specified, and `set_autostart` does
    nothing on Windows. Proposal: an `AppKata` value under
    `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` that runs `"…\appkata.exe" --tray`. It shows up in Task
    Manager → Startup apps, where the user can also turn it off. AppKata reads the value back to show the
    real state.
12. **appkata:// links (req 11.3).** The requirements mention only Linux. On Windows the handler is
    `HKCU\Software\Classes\appkata` (`URL Protocol`, `shell\open\command` = `"…\appkata.exe" "%1"`). The
    installer should register it, and the setting can register it for a portable or source run.
13. **One instance.** Clicking an `appkata://` link, or starting AppKata from the Start menu while it's in the
    tray, starts a second process. On Windows that happens on every link click. The requirements don't say
    that a second start hands its arguments to the running AppKata (a `QLocalServer`) and then exits. This
    isn't built on Linux either.
14. **Window frame (req 5.3).** The header bar is drawn by AppKata, and Windows users expect minimize and
    maximize buttons next to close. Aero Snap (dragging to an edge) and Windows 11's Snap Layouts (hovering
    over maximize) only work for frameless windows when they handle `WM_NCHITTEST`. Moving the window between
    monitors with different scale factors needs testing.
15. **Notifications (req 9.3).** Unless AppKata sets an AppUserModelID at startup and the Start-menu shortcut
    carries the same one, Windows attributes the toasts to "Python" or hides them. Clicking a toast that's
    already in the Action Center doesn't reach `QSystemTrayIcon.messageClicked`.
16. **Verifying downloads (req 4.4).** The requirements say to read Authenticode, but not how or what it shows.
    Proposal: `WinVerifyTrust` (with ctypes) on the `.exe`, `.msi` and `.msix`. A valid signature makes the chip
    **Verified**, and its tooltip names the signer. An invalid signature blocks the install, like a failed
    checksum. Separately, AppKata's downloads carry no Mark of the Web, so SmartScreen never checks them.
    AppKata should decide whether to add `Zone.Identifier` (as the browser does) or rely on its own checks.
    This is the Windows counterpart of the macOS quarantine question (§6).
17. **Windows on ARM (req 1.1).** The requirements promise arm64, but `build.md` ships x64 only and runs it
    under emulation. Choosing an asset needs a rule for arm64: prefer arm64, then fall back to x64 on Windows 11,
    which emulates x64. Windows 10 on ARM emulates only 32-bit x86, so the fallback doesn't work there.
18. **Foreign installs (req 4.5).** On Windows the requirements name only the Uninstall registry. Scoop
    (`~\scoop\apps`), Chocolatey (`%ProgramData%\chocolatey\lib`), winget (which reads the same registry) and
    Store or `.msix` apps (`Get-AppxPackage`) are left out. `foreign.inventory()` returns nothing on Windows.
19. **git and gpg (req 1.4).** "Explains how to install it" should be `winget install Git.Git`. Git for
    Windows puts only `cmd\` on the PATH. Its `gpg.exe` (in `usr\bin`) isn't found, so every GPG-signed Trust
    reports "gpg isn't installed". AppKata should look for gpg next to `git.exe` (`git --exec-path`) as well.
    Signing reviews with SSH needs OpenSSH 8.2+ (§15): check which `ssh-keygen` git uses on Windows.
20. **File names.** Slugs and version folders (`_safe`) can produce names that Windows reserves (`CON`, `NUL`,
    `AUX`, `COM1`…) or that end in a dot or space. Windows file names are case-insensitive, so `App` and `app`
    collide. Paths deeper than 260 characters (archives unpacked under `C:\Programs\<app>\<version>\`, and
    Trust clones) fail unless long paths are enabled. The requirements should cap the length or use `\\?\` paths.

### Gaps in the code

Beyond the gaps above:

- `install._activate` writes a Linux `.desktop` file on Windows instead of a Start-menu shortcut, and
  `_link` (command links) calls `os.symlink`, which fails without Developer Mode.
- `install._elevate` does nothing on Windows, and installers run through `subprocess` (see 1).
- `install.uninstall` refuses installer apps (see 4). `launch` uses `start_new_session`, which is POSIX-only. On
  Windows a launched app needs `DETACHED_PROCESS` or `os.startfile`, so that closing AppKata doesn't close it.
- `.msix` installs fail with "isn't supported on windows yet".
- `desktop.set_autostart` and `register_scheme` do nothing on Windows (see 11, 12).
- `foreign.inventory()` returns nothing on Windows (see 18).
- AppKata's own Source on Windows follows req 2.11.4 (notify only), because nothing adopts the installed copy
  (see 10).

### Packaging and testing

- The PyInstaller + Inno Setup build under Wine (`build.md` § Windows) isn't written. The installer has to
  answer: per-user or per-machine (`PrivilegesRequired=lowest` would match point 2), registering `appkata://`,
  an uninstaller that offers to remove `%LOCALAPPDATA%\AppKata`, and whether uninstalling AppKata leaves the
  apps it installed (proposal: it does, and says so).
- Code signing: there's no certificate yet. Until there is, SmartScreen warns on every download of the
  installer.
- Nothing has run on Windows yet. The shared Windows 10 VM (`build.md`) can run the unit tests, `appkata --tour`
  and real installs of an Inno app, an NSIS app, an MSI, a portable `.zip` and a Squirrel app.
- Mockups: only C09 is specific to Windows. Settings (X03, X05) shows Linux paths. A Windows set would add
  Settings with Windows paths, a UAC-elevated install in progress, "Close <App> to continue" (point 9) and the
  tray toast.

### Decisions needed

1. **Portable install folder:** `%LOCALAPPDATA%\Programs` (per user, private), or `C:\Programs` with tightened
   permissions (point 6).
2. **Installer scope:** prefer per-user installs where the installer supports them, and so avoid UAC (point 2)?
3. **Format order on Windows:** keep installers first (`.msi`, `.exe`, `.msix`, `.zip`), or prefer a portable
   `.zip` first, as Linux prefers the AppImage?
4. **Command links:** `.cmd` shims, or a small launcher `.exe`, in a folder AppKata adds to the user's PATH
   (point 8)?
5. **Window buttons:** add minimize and maximize to the header bar on Windows (point 14)?
6. **AppKata's own updates:** a silent run of the new setup with **Restart AppKata**, or notify only
   (point 10)?
7. **Mark of the Web:** tag downloads so SmartScreen checks them, or not (point 16)?
8. **arm64:** ship a native arm64 build, or x64 only with emulation, and drop "Windows 10 on arm64" from req 1.1
   (point 17)?

## 31. Windows decisions (2026-10-03)

The answers to §30's decisions are now in [`requirements.md`](requirements.md): §15, and the
sections it changes (1.1, 1.6, 1.9, 2.11, 4.2, 4.3, 4.9, 5.3, 11.1.4).

1. **Who an app is for:** a new per-app setting on Windows, **Just me** (the default, in
   `%LOCALAPPDATA%\Programs`) or **Everyone** (in `C:\Programs`). AppKata locks down the
   permissions of `C:\Programs` and of each app folder in it, so other accounts can't replace the
   programs (req 15.4).
2. **Installer scope:** per-user is preferred, and both scopes are offered wherever the installer
   supports them (MSI, Inno Setup, electron-builder's NSIS). Otherwise the installer decides, and
   AppKata records what happened (req 15.7.2, 15.8.1).
3. **Format order:** portable first: `.zip`, portable `.exe`, `.msi`, `.exe` installer, `.msix` (req 4.2,
   15.3).
4. **Command links:** `<app>.cmd` files in `%LOCALAPPDATA%\AppKata\bin`, which AppKata adds to the
   user's PATH (req 15.6). Known limits of `.cmd` files compared with a launcher `.exe`: Ctrl+C in a
   console app asks "Terminate batch job (Y/N)?", and `%` in arguments can be expanded by
   `cmd.exe`. Neither matters much for the GUI apps AppKata mostly installs.
   `current` is a directory junction, so shortcuts and `.cmd` files never need rewriting (req 15.5).
5. **Window buttons:** Minimize and Maximize/Restore on Windows, with Aero Snap and Snap Layouts
   (req 15.13).
6. **AppKata's own updates:** Track only and "updates itself" aren't opposites. Both stop AppKata
   from installing an app's updates. Track only also means AppKata never installs the app at all;
   "updates itself" means AppKata installs it but leaves updates to the app. For AppKata itself the
   built-in Source's **Track only** decides: off (the default) runs the new setup silently behind
   **Restart AppKata**; on means notify only, on every platform (req 2.11.5, 2.11.6).
7. **Mark of the Web:** a per-app setting, **Mark downloads as from the internet**, off by default.
   When it's on, SmartScreen checks the app's installers and programs as if a browser had
   downloaded them (req 15.11.1).
8. **arm64:** not supported on Windows; x64 only (req 1.1).

## 32. Building the Windows version (2026-10-03)

Windows is now built and tested (`docs/build.md` § Windows): real installs of five apps from
GitHub in the test VM, the unit tests under Python on Windows, and AppKata's own setup.

### Found and fixed

- **TLS certificates on Windows.** Python checks certificates against the roots already in
  Windows' store. Windows fetches missing roots when it needs them, but Python can't, so
  downloads from GitHub's file host failed with `CERTIFICATE_VERIFY_FAILED`. AppKata now checks
  certificates through Windows with `truststore`, a new dependency on Windows and macOS
  (req 15.17).
- **Newer Inno Setup installers weren't recognized.** Inno Setup 6.3 and later keep only UTF-16
  markers (`InnoSetupLdrWindow`), so Git for Windows' installer came out as "unknown" (req 15.7.1).
- **GitHub's pages, when the API is rate-limited** (affects Linux too). The releases feed of a
  monorepo lists bare tags first (ripgrep's `ignore-0.4.33`). They used up the three release
  pages AppKata reads for files, so ripgrep 15.2.0 seemed to have none. Now only releases with
  files count, up to eight pages.
- **`2.56.0.windows.1` was taken for a pre-release** (affects Linux too): any word after the
  version counted as a pre-release label. Now only pre-release words do (alpha, beta, rc,
  pre, preview, dev, nightly, snapshot, and `a1`/`b2`).
- **"Held · N days left"** was a day too long when the time left was a whole number of days.
- **Update all also updated Track-only apps** (req 9.4). It no longer does, and Track only on
  AppKata's own Source makes it notify only (req 2.11.6).
- **Quit AppKata in the tray menu raised an error** unless AppKata was started from a link (an
  import inside `main()`).
- **File dialogs on Windows** got `file://C:/…` URLs, which hid every icon and broke the folder
  pickers (`Theme.fileUrl`, `Theme.localPath`).

### Decided while building (not asked)

- **Shortcuts for other apps get no AppUserModelID.** One that the app doesn't use itself breaks
  pinning and grouping on the taskbar. Only AppKata's own shortcut has one (req 15.5).
- **An untrusted signature counts as unsigned, not as a failure** (req 15.11). Many FOSS projects
  sign with certificates Windows doesn't trust. A signature that doesn't match its file still
  blocks the install.
- **`.cmd` command links carry a first line, `@rem made by AppKata`,** so AppKata knows which
  ones it wrote (req 15.6).
- **One AppKata at a time is per user and per data folder** (req 1.9), so the tests and the demo
  can run beside a real copy.
- **Folders for everyone are repaired, not refused, when the user or Administrators own them**
  (req 15.4.3).

### Still open

- **The Visual C++ run-time** is now req 15.18, and built: tested in the VM with hyperfine. Some portable apps
  need `VCRUNTIME140.dll`: hyperfine's `.zip` exits with `0xC0000135` on a fresh Windows. One
  package, the 2015–2022 Redistributable (x64), covers them. AppKata detects the need from each
  program's imports and shows an **MSVCRT** chip (tooltip "Microsoft Visual C++ Run-time"). It
  offers to install Microsoft's signed package with one administrator prompt, and never removes it.
  Older run-times (2005–2013) and app-local copies of the DLLs are out of scope.
- **Not testable headless in the VM:** a UAC prompt answered by a person, SmartScreen with Mark
  of the Web on, Windows 11's Snap Layouts (the VM runs Windows 10; the hit test that enables them
  passes), and live Squirrel and `.msix` installs (no small FOSS release to try). These need a
  manual check on a real Windows 10 and Windows 11 PC.
- **AppKata's own update end to end** needs a published release. AppKata's repository was still
  the placeholder (it is `github.com/MojoKata/AppKata` since 2026-10-25). Running the setup with `/RELAUNCH=1` while AppKata runs was tested: it closes
  the running AppKata, installs, and starts the new one.
- **The shared test VM's evaluation licence has expired.** Windows shuts down about an hour after
  each start. It needs rebuilding (the VM's own README describes how); that also affects the other
  projects that share it.
- **Code signing** for AppKata's own setup still needs a certificate.

## 33. Package channels and version reviews (2026-10-05)

### Version reviews (req 8.4, 10.3, 10.6.5)

- **Reviews are point-in-time.** "I tried 2.0.1, here's what I think" holds for 2.0.1 and later
  until the reviewer says otherwise. A version review is `## <App>[<version>]`, with optional
  `### <App>[<version>]::Details` (what was installed) and `### <App>[<version>]::Settings`
  (Trust, Rating, Tags and options that change from that version on).
- **No version ranges.** A sequence of version reviews describes every case we tried, including
  advisories (`xz[5.6.0]` Trust 0, `xz[5.6.2]` Trust 4) and "no fix yet" (the veto holds for later
  versions until lifted, so it fails safe). Explicit ranges mostly add ways to stop covering new
  releases by mistake.
- **"::AppKata" is dropped from headings**: the file is `AppKata.md`. `## <App>::AppKata::Settings`
  is now `## <App>::Settings` (done in the parser, `docs/AppKata.md`, the generator, the demo data
  and the tests). Nothing is fielded, so no compatibility is kept.
- **Details sit with their review**, not in one `::Reviewed` block, since what was installed differs
  from one review to the next.
- **The table row is the newest review's verdict** and wins over the newest review's Settings, so
  readers of the table and AppKata agree. Settings carry forward: a version review only states what
  changes; Tags replace the whole list.
- **Versions in headings are the project's**, not a package's (`1.2.3`, not `1.2.3-4`). Reviews are
  placed with 9.4's comparison, falling back to release dates, instead of a new ordering.
- **No checkbox for "save as a new review"**: the Version select decides which review is edited.
- **Deferred:** reviews of a distribution's own revision (patched or backported builds). Version
  reviews of the project are enough until real use shows otherwise.
- **Built** (2026-10-05). Version reviews are stored in the existing `reviews.settings` JSON. A
  Trust or Rating left empty isn't written as a line, so in a version review it carries the previous
  value forward; "no opinion" can only be given in the table row or the app review.

### Package channels (req 16)

- **An app is still its git URL.** Flatpak remotes and the distribution's repositories are channels
  for it. Channels don't add apps to the Catalog; Explore finds them, and adding one needs the git
  URL (from AppStream, or typed in).
- **Apps, not packages:** only AppStream components of type `desktop-application` and
  `console-application` are used, without parts of the desktop and Ubuntu's Snap transitional
  packages. Browsing every package is out of scope.
- **Linking** comes from the user, then a Trust (`Flatpak`, `Debian package`, `Fedora package`
  lines), then AppStream URLs; every link is checked against the project (metainfo ID, Flathub's
  verified flag and manifest, Debian and Fedora packaging metadata). A failed check is a warning,
  not a block.
- **Updates: the system first.** When the system updates an app automatically, AppKata tracks it
  (**Updated by the system**) and doesn't compete; when nothing does, the app is flagged **Not
  updated automatically** and AppKata offers its updates. The user can switch to **AppKata
  updates it** in Install options. Automatic updates are detected from unattended-upgrades
  (including its origins: security-only doesn't count), dnf-automatic, GNOME Software, Discover and
  Mint's Update Manager, and afterwards from apt, dnf and flatpak history.
- **Package backend: PackageKit over QtDBus, with the command line as fallback.** QtDBus is part of
  PySide6, so this adds no dependency. PackageKit is what GNOME Software and Discover use: AppKata's
  installs queue with theirs instead of fighting over the dpkg/rpm lock, polkit keeps the password
  for a few minutes (one prompt for Update all), and it gives progress, cancel and dry runs. The
  command line through `pkexec` covers servers and minimal installs, with the known apt pitfalls
  handled: the lock (wait and say who holds it), debconf and configuration-file prompts
  (`noninteractive`, `--force-confdef/--force-confold`), removals cascading to dependent packages
  (dry run first, list what goes, refuse metapackages and essential packages).
- **Found:** `uninstall()` runs `apt-get remove -y` / `dnf remove -y` without a dry run, so removing
  a `.deb`/`.rpm` app can also remove packages that depend on it. Req 16.4.3's dry run fixes it for
  release packages too.
- **Pinning** a Flatpak uses `flatpak mask`, which also stops the desktop's store; packages can't be
  pinned from AppKata (`apt-mark hold` and `dnf versionlock` change the whole system).
- **Recommended card order** without a Trust's `Channel` line (decided while writing, easy to
  change): a verified Flatpak, then release files, then a community Flatpak, then the distribution's
  package.
- **Supported:** Debian, Ubuntu, Mint, Fedora, and now RHEL, AlmaLinux and Rocky Linux 9+ (their
  glibc 2.34 is newer than the AppImage's 2.28 floor). openSUSE (zypper) is out.
- **Built** (2026-10-05), except installing an older Flatpak commit from the Versions list
  (read-only for channel installs for now) and distribution patch counts. The install dialog's
  cards: mockup `screenshots/mocks/*/C10-install-channels.png`, real screen
  `screenshots/linux/*/C10-install-channels.png`; compare with C06.
- **Decided while building:** PackageKit is driven by a small pure-Python D-Bus client
  (`dbus.py`), since QtDBus can't send PackageKit's unsigned 64-bit flags. A cascade on uninstall
  asks for confirmation (listing what goes) rather than being refused; essential packages, desktop
  metapackages and packages that are only dependencies are refused. Only automatic updaters move
  an app from **Not updated automatically** to **Updated by the system**. Flathub online search
  reads each hit's AppStream entry for its project URL (up to 15 requests).
- **Unverified on real systems:** Mint Update Manager's automation flags, the GNOME Software
  gsettings key on every release, and PackageKit's waiting-for-lock status number.

### Resolved after round 33 (2026-10-05)

- **When link checks run** (req 16.1.5): the verified flag every sync, as a conditional request;
  the Flathub manifest only when the Flatpak's commit changes, read as a raw file so it doesn't

- **Linux distribution** (req 1.6, 2.11.3.1): the AppImage only. It runs without `libfuse2` (the
  static type-2 runtime needs only `fusermount`/`fusermount3`; checked on Ubuntu 24.04), and on
  first start it offers to install itself: a copy in the install folder with the stable-name link,
  an app-menu entry and icon, and the `appkata://` handler and autostart pointed at the stable link.
  **No Flatpak**: it would need the home folder, `flatpak-spawn --host` and PackageKit's D-Bus name,
  which opens the sandbox to the host and is unlikely to pass Flathub. **`.deb`/`.rpm` are a

  competing with apt or dnf, so it would need its own repositories to update well.


## 16. App sandboxing (resolved 2026-10-09)

These answers are now part of [`requirements.md`](requirements.md) (§17); the rationale, experiments
(three rounds, `scripts/sandbox/`) and mockups are in [`app-sandboxing.md`](app-sandboxing.md), and the
human validation checklist in [`local-proxy-test-plan.md`](local-proxy-test-plan.md).

1. **Mechanism:** bubblewrap + xdg-dbus-proxy, unprivileged; no Firejail (setuid), no systemd-run.
   Landlock only later, as a layer *inside* bwrap, never a standalone fallback (it can't mediate the
   session D-Bus socket, so alone it can't stop a systemd escape) (req 17.1, 17.18).
2. **Levels and defaults:** Off / Standard / Strict. Reviewed beats unreviewed; unreviewed GUI →
   Strict, unreviewed CLI → the CLI tool template, reviewed → the review's template (req 17.2, 17.3.3).
3. **Templates:** eight built-in, thin and overridable, resolved to a grant set before merging;
   several Trusts → strictest level + intersection of grants; user choice wins (req 17.3).
4. **CLI tools get real protection,** not Off: the CLI tool template binds only the directory the tool
   is run in (req 17.3.3).
5. **AppImages:** run the `.AppImage` directly at Off; lazy sandboxed extraction for Standard/Strict
   (the `.AppImage` is canonical, the extracted dir a cache) (req 17.7).
6. **AppArmor:** where the kernel restricts unprivileged user namespaces the sandbox needs a profile
   (which tested systems: `docs/testing.md`); AppKata installs it on first need behind one pkexec
   prompt; declined → Off with a warning (req 17.10).
7. **Wayland deferred:** the security-context protocol is post-v1; v1 warns that the screen, the
   clipboard and keystrokes aren't protected on X11 and on every Wayland compositor but GNOME's (on
   KDE the clipboard alone), judging the compositor by the globals it offers as well as its name
   (req 17.9).
8. **Reviews never auto-change grants:** a new version keeps the user's grants and raises a review
   badge (req 17.11).
9. **Self-update:** an app that updates itself can't while sandboxed (read-only files), so AppKata
   updates it then, as if it didn't (req 4.10.5, 17.12; review 2, F3 — the earlier "disable the app's
   own updater" option contradicted 4.10.3 and was never built).
10. **Enabling a sandbox later** warns the app is effectively reinstalled and its config may reset; no
    automatic import in v1 (req 17.13).
11. **Desktop integration:** themes/fonts bound read-only; the app owns its bus name and its template's
    capabilities (tray, MPRIS, inhibit, secrets, notifications); a stable `io.appkata.<app>` identity
    (`.flatpak-info`) that PipeWire and GLib rely on (files are handed over through the document
    portal from the host side, req 17.6.2); sound as a sandboxed client, not
    the raw socket; device tools (Ventoy) legitimately run Off (req 17.4–17.8).
12. **Not sandboxed yet / separate:** personal and reviewer-defined templates, config import, a fuller
    seccomp filter (the terminal-injection one is built), squashfuse, NVIDIA nodes, and App categories in the Catalog (req 17.18).
