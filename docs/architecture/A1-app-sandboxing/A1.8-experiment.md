# A1.8. Experiment

The experiments behind the design: three rounds, reproducible through `scripts/test-sandbox.sh <mode>` (Docker; the `apparmor` mode also
needs `/dev/kvm`) and the round-3 probes run directly in the session container. The probes live in
`scripts/sandbox/`:

| Mode / probe | What it does | Key scripts |
|---|---|---|
| `probe` | The hostile-app probe in Mint 21.3 and 22.1 containers (table below) | `probe.sh`, `probe.lua` |
| `gui` | AppKata (Qt) and Obsidian (Electron) on Xvfb/X11, screenshots | `gui.sh` |
| `session` | Round 2 display/sound/portals in a Mint 22.1 Wayland container (sway + mutter, PipeWire, portals) | `session.sh`, `lib.sh`, `display.sh`, `sound.sh`, `portals.sh`, `filechooser.sh`, `apps-wayland.sh`, `typebox.py` |
| `apparmor` | Round 2 AppArmor/userns in a real Ubuntu 24.04 VM under KVM | `vmtest.sh` |
| round 3 | De-risking: theme/font binds, D-Bus own-name/caps, write-beside-itself, the full launcher, portal identity, and the merge rule | `validate2.sh`, `validate-launcher.sh`, `validate-portal.sh`, `merge.py` |
| review | The file-chooser call through a generated launcher: showed xdg-desktop-portal 1.18+ refusing the marked caller (R17.6.1, `docs/reviews/app-sandboxing-1.md` finding 0); since the decision it shows the proxy's own AccessDenied, the portal never asked | `validate-chooser.sh` |
| `filedialogs` | Which file dialog real GTK3, GTK4 and Qt 6 apps show behind a generated launcher, with the portal and its gtk backend on the bus, and which proxy denial makes it so (R17.6.3; round four R4-5): their own, GTK4 held by the FileChooser denial, GTK3 and Qt 6.4 never asking | `filedialogs.py` |
| `consumers` | Real consumers behind generated launchers, with the real portal, its gtk backend, a stand-in notification daemon and the test link handler on the host: a GLib app's notification reaches the host daemon with the capability and nowhere without it (R17.5.1, R3-6); a GTK3 app's link runs the host's handler on the host, never inside (R17.6.3, R3-1); Chromium 154 shows its own GTK file dialog as generated, *no dialog* with only Properties allowed (it reads `version`, takes the portal road, is refused `OpenFile`), the portal's with FileChooser allowed too — the Properties denial is load-bearing for Chromium/Electron and for it alone (R4-5) | `consumers.py` |

`lib.sh` holds the `sbx` helper that builds the Standard/Strict bwrap command the tests exercise;
`session.sh` brings up the headless desktop session. Output and screenshots land in
`build/sandbox-test/`.

**What the harness needs** on a host with an older kernel, no desktop and no GPU, where everything
runs in containers and VMs:

- A 4.18 kernel has **neither** the Ubuntu userns restriction **nor** Landlock, so both round-2
  questions need the Mint containers or the Ubuntu VM, not the host.
- Containers must run with `--security-opt seccomp=unconfined --security-opt systempaths=unconfined
  --security-opt apparmor=unconfined` (and `--device /dev/fuse --cap-add SYS_ADMIN` for the Wayland
  session) so bwrap can nest. On a real desktop none of that is needed.
- The session container takes most packages from Ubuntu's `archive.ubuntu.com` rather than Mint's
  own servers (`packages.linuxmint.com`), which are often unreachable from a test network.
- The Ubuntu 24.04 VM uses the cloud image from `cloud-images.ubuntu.com` + cloud-init; `qemu` runs
  inside a container with `/dev/kvm` passed through. The cloud image has **polkit but not `pkexec`**
  installed (a real Mint desktop has both; AppKata assumes pkexec for packages).
- A known harness limitation: `filechooser.sh`'s document-portal re-export step fails on nested-bwrap
  socket propagation (a test-rig issue, not a finding). The design-relevant half, that a picked path
  is unreadable inside the private home without the portal, passes.

`scripts/test-sandbox.sh probe` runs in Docker (Mint 21.3 and 22.1 images). The containers run with
seccomp, AppArmor and `/proc` masking opened so bwrap can nest; on a real desktop that isn't needed.

**Probe.** A user `kata` with a fake SSH key, Firefox cookies, `~/Documents/taxes.txt`,
`GITHUB_TOKEN` in the environment, another installed app, a second process (`secret-agent`) and a
session bus with another app's service (`org.example.Secrets`). Neovim's official AppImage,
installed in `~/bin/apps/nvim/0.11/` as AppKata lays it out, runs `scripts/sandbox/probe.lua`
(`nvim -l`), playing a hostile app. Afterwards the harness checks the **real** files. The result is
the same on Mint 21.3 (bwrap 0.6.1) and 22.1 (bwrap 0.9.0):

| Attempt | Unsandboxed | Standard | Strict |
|---|---|---|---|
| Read `~/.ssh/id_ed25519` | Leaked | Blocked | Blocked |
| Read Firefox cookies | Leaked | Blocked | Blocked |
| Read `~/Documents/taxes.txt` | Leaked | Leaked (granted) | Blocked |
| Read `$GITHUB_TOKEN` | Leaked | Blocked | Blocked |
| Append to `~/.bashrc` | **Real file changed** | Private home only | Private home only |
| Autostart entry, systemd user unit, hijacked menu entry | **Real files changed** | Private home only | Private home only |
| Write into its own install folder | **Changed** | Blocked (read-only) | Blocked |
| Modify another installed app | **Changed** | Private home only | Private home only |
| TCP connect to github.com:443 | Yes | Yes | Blocked |
| See the user's other processes | Yes | Blocked | Blocked |
| Reach the session bus | Yes | The proxy only | No bus |
| Call `org.example.Secrets` | Yes | Blocked by the filter | Blocked |
| Its own settings | Work | Work (private home) | Work (private home) |
| Run the `.AppImage` file itself | Works | Fails: no FUSE | Fails: no FUSE |

**GUI apps** (Mint 22.1, Xvfb, Standard profile with X11, `/dev/dri` if present and the D-Bus
proxy): AppKata's own AppImage (Qt 6) and Obsidian 1.14.4 (Electron) both start, draw their first
window and are still running after 15 s; Obsidian's Chromium sandbox works inside bwrap and it
reaches GitHub for its update check. AppKata, started for the first time in its private home,
installs itself there (R2.11.3), harmlessly.

## A1.8.1. Round 2: display, sound, portals, Ubuntu 24.04

The second round (`scripts/sandbox/` driven by `scripts/test-sandbox.sh session|apparmor`) covers
what the first leaves out: a Mint 22.1 container with a headless **sway** (Wayland, no XWayland),
**mutter 46** as a second compositor, **PipeWire** and the **xdg-desktop-portal** stack; and, for
AppArmor, a real **Ubuntu 24.04** VM booted under KVM (its own 6.8 kernel, which a container can't
provide). What it shows:

- **Ubuntu 24.04 blocks bwrap outright, so AppKata ships an AppArmor profile.** On a stock 24.04
  VM (`kernel.apparmor_restrict_unprivileged_userns = 1`), a plain `/usr/bin/bwrap` run from a login
  shell **fails** in every profile: `setting up uid map: Permission denied`, or, once a net namespace
  is made, `loopback: Failed RTM_NEWADDR`. Plain `unshare --user` is denied too. The system's loaded
  `unprivileged_userns` AppArmor profile is why. The fix every sandboxing app already uses: ship an
  AppArmor profile that grants the carve-out — the VM has `/etc/apparmor.d/` profiles for `flatpak`,
  `chrome`, `obsidian`, `signal-desktop`, `code`, `1password`, `element-desktop`, `steam` and more.
  A four-line profile for bwrap (`profile appkata-sandbox /usr/bin/bwrap flags=(unconfined) { userns, }`)
  makes bwrap **work**, including the **nested** user namespace that Electron/Chromium's own sandbox
  needs. A third VM run checks the privilege model (see [bubblewrap](A1.2-approach.md#a121-bubblewrap)): an unprivileged
  user cannot write `/etc/apparmor.d/`, run `apparmor_parser`, or set the sysctl (all denied), so the
  profile is installed **on first need** behind a single **pkexec** prompt and then persists across
  reboots (`apparmor.service` is enabled and reloads the profile at boot). Disabling the sysctl also
  works but weakens the whole system. Where the user declines, the app runs Off (R17.10): there is
  no Landlock-only fallback (A1.12.6), since Landlock can't mediate the session bus. Mint 21.3
  (bwrap 0.6.1) has no such restriction, and Mint 22 lifts the one of the Ubuntu it is built on in
  its own `/etc/sysctl.d/20-apparmor-mint.conf`, as the Mint 22.3 desktop VM shows (review 3, R3-37).

- **Wayland isolation is compositor-dependent, not automatic.** On **sway** (and other wlroots
  compositors that enable the `wlr-screencopy`, `wlr-data-control` and `virtual-keyboard` protocols),
  a sandboxed app given only the Wayland socket can still **capture the whole screen**, **read the
  clipboard while unfocused**, and **type into another app's window**: the same three leaks as X11.
  On **mutter** (GNOME, and the base of Cinnamon's muffin) all three are **blocked**: it doesn't
  offer those protocols, and screencast goes through the portal with user consent. The fix for
  wlroots is the Wayland **security-context** protocol (the Wayland analog of the D-Bus proxy): the
  launcher would tag the app's connection so the compositor withholds the privileged protocols.
  AppKata doesn't use it (A1.12.9, R17.18): it needs a real wlroots desktop to validate. AppKata
  **warns** on X11 and wlroots sessions instead; only mutter-style Wayland is clear. Sway's IPC
  socket is **not** reachable (it isn't under the bound socket path), which matters, since it runs
  arbitrary commands: the launcher never binds all of `$XDG_RUNTIME_DIR`.

- **Sound: playback is fine, but the raw socket also grants recording and server control.** With the
  PipeWire and PulseAudio sockets bound in, playback works (and is **blocked** without the grant).
  But the same socket lets the app **record the microphone and a monitor of what other apps play**
  (it captures another app's tone at full amplitude), and **load PulseAudio server modules**
  (`module-pipe-sink`, `module-native-protocol-tcp`) that run outside the sandbox. So "sound" can't be
  a single raw-socket grant. The mitigation is real: a client launched with a `.flatpak-info` marker
  is classified by PipeWire as `pipewire.access: flatpak` / `pipewire.sec.flatpak: true`, the hook
  WirePlumber uses to restrict recording and module loading per app. So the audio goes where the
  session manager sees the app as sandboxed (the marker), rather than through a bare socket, and the
  grant is split into **play** and **record** (R17.8).

- **The D-Bus filter holds, and the file-chooser needs the document portal.** Through the filtered
  bus a sandboxed app reaches **only** `org.freedesktop.portal.Desktop` (FileChooser, OpenURI,
  DynamicLauncher, each applying its own policy) and is **blocked** from `org.freedesktop.systemd1`,
  `org.freedesktop.Flatpak`, `org.freedesktop.portal.Documents` and `org.freedesktop.secrets`. A path
  the user would pick in a file dialog (e.g. `~/Documents/secret.txt`) is **not** readable inside the
  private home, so a file reaches the app through the **document portal**, which re-exports just that
  file. This is standard Flatpak mechanics; A1.8.2 and A1.12.16 say how AppKata does the hand-over.

- **Real GUI apps on Wayland only.** AppKata's own Qt AppImage and Obsidian 1.14.4 (Electron, run with
  `--ozone-platform=wayland`) both start and keep running in the Standard profile with only the sway
  Wayland socket, sound and the filtered bus, and no X server. Screenshots in `build/sandbox-test/`.

## A1.8.2. Round 3: the mechanisms the design leans on

The third round checks the mechanisms the design leans on (`scripts/sandbox/validate*.sh`, `merge.py`):

- **Theme/font binding — confirmed.** A private home hides the host's `~/.themes`/`~/.fonts`; binding
  them read-only makes them visible again and they stay read-only, so apps look native.
- **D-Bus capabilities — confirmed.** Through the proxy an app **can** own its own granted name
  (single-instance, "open in running window") and **cannot** own a name that wasn't granted. The
  capability model (own/talk per template) works as designed.
- **Write-beside-itself + the writable-app-folder grant — confirmed.** Under Standard, writing next to
  the binary is blocked (read-only); the grant binds the folder read-write and the write succeeds.
- **Full launcher, end to end — confirmed.** AppKata (Qt) and Obsidian (Electron) both run under the
  *complete* Standard launcher — identity marker + filtered proxy (own-name + a capability) + theme/font
  binds + a folder grant + network + X11 + sound — and `~/.ssh` stays blocked with all of it composed.
  The whole mechanism holds together, not just the pieces.
- **Multi-Trust merge — tested.** `merge.py` implements the resolution rule (A1.12.13) and its cases
  pass, including the "two different templates" case.
- **App identity for portals.** The synthetic `.flatpak-info` changes how the document portal treats
  a caller, and PipeWire takes it (`access=flatpak`); the private home blocks the raw path. But on
  xdg-desktop-portal 1.18 and later (1.20 on Mint 22.1 and Ubuntu 24.04) a generated launcher's
  `FileChooser.OpenFile` call is refused, "Portal operation not allowed: Failed to open file
  …/.flatpak/<instance>/bwrapinfo.json", because the portal validates a marked caller against a live
  Flatpak instance (review). So (R17.6.1, A1.12.15) the bus proxy carries no marker, the portals see a
  host caller, the file chooser portal is not used, and file arguments are handed over from the host
  side, all shown end to end in the containers (`tests/test_sandbox_run.py`,
  `scripts/test-sandbox.sh filedialogs` and `consumers`).

**What only a physical desktop shows**: real GPUs (a VM has only a virtual adapter; the VM shows the
`/dev/dri` nodes resolve through `/sys`); a self-updating app sandboxed (round 1 shows the write to
its own folder is blocked, so the updater fails; how each app takes that is the question); the
pkexec prompt where the setup is needed (R17.10); a tray icon against a real StatusNotifierWatcher;
and a full run in a physical Mint 22 session (Cinnamon/X11) and a GNOME/Wayland one. These are the
human checklist in [`local-proxy-test-plan.md`](../../local-proxy-test-plan.md), which
`scripts/sandbox/field-test.sh` runs against a probe app AppKata itself installs. The containers,
with the real portal and real apps, show the document-portal hand-over, the portals as a host
caller, the toolkits' file dialogs, notifications and link opening.
